# PHASE 3 — VERTICAL SLICE

**Project:** GeoStrom AI · **Phase:** 3 · **Status:** Complete · **Scope:** Integration proof, not the final product

> **Data legend, carried over from Phase 2 and enforced end-to-end through this phase:**
> **OBSERVED** — a value read from IBTrACS via the Phase 2 artifact, unmodified.
> **MODEL PREDICTION** — output of a Phase 2 baseline model, persisted verbatim.
> **DERIVED** — a deterministic transform of the above (Haversine error, Saffir-Simpson category from wind).
> These three categories are distinguished in the database (`observations` vs. `predictions` tables), the API (`data_kind` field, `properties.kind` on GeoJSON features), and the UI (colour, line style, and literal on-screen labels).

---

## 1. Objective

Prove the first complete, real, end-to-end path through the architecture:

```
Phase 2 baseline predictions (ml/reports/phase2_test_predictions.parquet)
        ↓  backend/scripts/ingest_phase2_predictions.py
PostgreSQL + PostGIS  (persistence layer)
        ↓  backend/app  (FastAPI, read-only)
API contract  (contracts/openapi.json, generated)
        ↓  frontend/lib/api-types.ts  (generated)
Minimal frontend  (Next.js + Leaflet)
        ↓
Interactive storm track map — observed vs. predicted, visually distinct
```

Every link in that chain was built, run, and verified against real data in this session — not
mocked, not simulated. Where a real Postgres/PostGIS instance, a real FastAPI process, and a real
Next.js dev server were required, they were actually started and queried.

## 2. Architecture Implemented

The Phase 0 offline/online boundary (`docs/SYSTEM_ARCHITECTURE.md` §1) is preserved exactly:

```
OFFLINE (ml/, Phase 2 — already complete, untouched)
   Persistence / Ridge / LightGBM baselines → ml/reports/phase2_test_predictions.parquet
                                    │
                                    ▼  backend/scripts/ingest_phase2_predictions.py
                                    │  (standalone script; NOT part of the served app)
                                    ▼
ONLINE (backend/, this phase)
   PostgreSQL + PostGIS  ←──────────┘
        │  SQLAlchemy 2.0 ORM (backend/app/db/models.py)
        ▼
   FastAPI (backend/app/main.py) — read-only, zero ML imports in the request path
        │  Pydantic v2 schemas (backend/app/schemas/)
        ▼
   contracts/openapi.json  (generated from the running app, never hand-written)
        │  openapi-typescript
        ▼
   frontend/lib/api-types.ts  (generated, never hand-edited)
        │
        ▼
   Next.js 15 + Leaflet  (frontend/)
```

**Verified, not assumed:** `backend/app/` imports nothing from `ml/` — checked by inspection of
every import statement in `backend/app/`. The one place the offline and online worlds meet is
`backend/scripts/ingest_phase2_predictions.py`, which is a standalone script, never imported by
`app.main`. Section 15 below explains the one narrow, deliberate exception this required.

### 2.1 A design finding worth recording

Before writing the ingestion script, the actual schema of `ml/reports/phase2_test_predictions.parquet`
was inspected (not assumed). This surfaced a useful structural fact: because Phase 2's sliding
windows use stride 1, a storm's window reference timestamps (`t_ref`) form an exact, gap-free
6-hourly sequence — verified empirically across all 88 test storms, zero exceptions. This means the
**complete observed track** for each storm's test-eligible span can be reconstructed from the
predictions artifact alone (every window's reference point, plus the last window's +6/+12/+18/+24h
ground-truth targets) — with **no need to re-load raw IBTrACS and no need to import any Phase 2
feature-engineering code into the backend.** This is what keeps `backend/` fully independent of
`ml/`, as the architecture requires, without duplicating Phase 2's causal-window logic.

## 3. Database Schema

**Engine:** PostgreSQL 16 + PostGIS 3.4, via `postgis/postgis:16-3.4` (Docker). Schema created by
Alembic migration `0001_initial_schema` — hand-authored rather than autogenerated (see §4) — and
matches `docs/SYSTEM_ARCHITECTURE.md` §7.2's preliminary schema, scoped to what Phase 3 needs.

**Tables built:** `model_versions`, `storms`, `observations`, `predictions`. **Not built:**
`detections`, `classifications`, `forecast_cones` — no detection/classification model exists yet
(Phase 5/6, explicitly out of Phase 3 scope), so those tables would be speculative schema for models
that don't exist. Adding them now would violate the project's own scope-creep guard.

### 3.1 `model_versions`

| Column | Type | Notes |
|---|---|---|
| `id` | `integer` PK | |
| `name`, `version` | `varchar` | UNIQUE together, e.g. `('track_cliper', 'v1')` |
| `task` | `varchar` | `'track'` \| `'intensity'` |
| `trained_at`, `dataset_build`, `split_version`, `feature_version` | | copied verbatim from Phase 2's benchmark record |
| `config` | `jsonb` | model hyperparameters, verbatim from Phase 2 |
| `metrics` | `jsonb` | **verbatim Phase 2 test-set metrics**, keyed by horizon string (`"6"`, `"12"`, `"18"`, `"24"`) — never recomputed |
| `error_radii_km` | `jsonb`, nullable | track models only: mean historical error per horizon, for a future uncertainty-cone feature |
| `is_active` | `boolean` | |

### 3.2 `storms`

Matches `docs/SYSTEM_ARCHITECTURE.md` §7.2 exactly, including the schema's own warning comment
carried into `backend/app/db/models.py` verbatim: *"Lifetime summary fields — DISPLAY ONLY. Never
fed into a model feature pipeline."* `track_geom` (`GEOGRAPHY(LINESTRING,4326)`) and `bbox`
(`GEOGRAPHY(POLYGON,4326)`) are built once at ingestion time from the reconstructed observed track.

### 3.3 `observations` — **long form**, one row per (storm, timestamp)

`lat DOUBLE PRECISION NOT NULL`, `lon DOUBLE PRECISION NOT NULL`, `geom GEOGRAPHY(POINT,4326) NOT
NULL`, plus `CHECK (lat BETWEEN -90 AND 90)` and `CHECK (lon BETWEEN -180 AND 180)` — enforced by
Postgres itself, not just application code (verified in `tests/test_db_constraints.py`, §10).
`UNIQUE(sid, ts)`.

### 3.4 `predictions` — **long form**, per the Phase 0 locked decision

> "one prediction row = one storm + one initialization time + one horizon + one target/model/version combination"

```sql
UNIQUE (sid, origin_ts, lead_hours, model_id)
CHECK (lead_hours > 0)
CHECK (pred_lat IS NULL OR pred_lat BETWEEN -90 AND 90)
CHECK (pred_lon IS NULL OR pred_lon BETWEEN -180 AND 180)
CHECK (true_lat IS NULL OR true_lat BETWEEN -90 AND 90)
CHECK (true_lon IS NULL OR true_lon BETWEEN -180 AND 180)
```

A track model's row populates `pred_lat`/`pred_lon`/`pred_geom`/`track_error_km` and leaves
`pred_wind_kt` null; an intensity model's row is the reverse. **Adding a 48h horizon later is one
more `INSERT`, never a schema migration** — proven by design, not just claimed: the table has no
`pred_lat_6h`/`pred_lat_12h`-style wide columns anywhere.

One deliberate, documented addition over the `SYSTEM_ARCHITECTURE.md` sketch: a `task` column
(`'track'` \| `'intensity'`), because Phase 2 produced two disjoint model families and `task` makes
that partition queryable without inspecting which columns are non-null.

### 3.5 Indexes

`ix_storms_season`, `ix_storms_basin_season`, `ix_storms_split`, `ix_storms_track_geom` (GIST),
`ix_observations_sid_ts`, `ix_observations_geom` (GIST), `ix_predictions_sid_origin`,
`ix_predictions_model_lead`, `ix_predictions_task`, `ix_predictions_pred_geom` (GIST) — covering
every lookup pattern the API actually issues (storm-by-season list, observations-by-storm-ordered-
by-time, predictions-by-storm-and-origin, predictions-by-model-and-horizon).

### 3.6 Final row counts (this session, real ingestion of the real Phase 2 test artifact)

| Table | Rows |
|---|---|
| `model_versions` | 6 |
| `storms` | 88 |
| `observations` | 2,084 |

## 4. Migration Instructions

```bash
# 1. Start PostgreSQL + PostGIS
cp infra/docker/.env.example infra/docker/.env   # set a real local password
docker compose -f infra/docker/docker-compose.yml up -d

# 2. Configure the backend
cd backend
cp .env.example .env                              # set DATABASE_URL to match infra/docker/.env
pip install -r requirements.txt

# 3. Enable PostGIS on the database (once)
python -c "
import psycopg2, os
conn = psycopg2.connect(os.environ.get('DATABASE_URL', '...').replace('+psycopg2',''))
conn.autocommit = True
conn.cursor().execute('CREATE EXTENSION IF NOT EXISTS postgis')
"

# 4. Run migrations
python -m alembic upgrade head
```

**Why the initial migration is hand-authored, not autogenerated:** `alembic revision --autogenerate`
was run first, against a real `postgis/postgis` container. It picked up ~40 pre-existing TIGER
geocoder and topology tables (`spatial_ref_sys`, `topology`, `tract`, `county`, ...) that ship with
the PostGIS image itself, and proposed **dropping all of them** as part of the "diff." Auto-including
that would have made the first migration destructive against PostGIS's own extension-owned schema.
The autogenerated file was discarded; `backend/alembic/versions/0001_initial_schema.py` is
hand-written, touching only the four GeoStrom AI tables plus `CREATE EXTENSION IF NOT EXISTS
postgis`. **Migration reproducibility is verified by an actual test** (`tests/test_migrations.py`):
it drops and recreates a throwaway database, runs `alembic upgrade head` against it as a real
subprocess, and asserts every expected table, the PostGIS extension, and every GIST geometry index
exist — this is not a claim, it is a passing test (§10).

## 5. Ingestion Process

**Script:** `backend/scripts/ingest_phase2_predictions.py`. **Inputs:**
`ml/reports/phase2_test_predictions.parquet`, `ml/reports/phase2_benchmark_results.json`,
`ml/manifests/splits_v1.json` — all pre-existing Phase 1/2 artifacts. **Nothing is downloaded,
nothing is retrained, nothing is recomputed differently from Phase 2** (see §15 for the one
narrow exception, and how it's proven to match).

### 5.1 Validation performed (all fail loudly, none silently)

| Check | Method |
|---|---|
| Required columns present | set-difference against the exact expected schema (base columns + 4 horizons × (3 target fields + 6 model-output fields)) |
| `t_ref` is a real datetime column | `pandas` dtype check |
| Storm IDs match IBTrACS SID grammar | regex `^\d{7}[NS]\d{5}$` |
| Latitude/longitude in range | `-90..90` / `-180..180` on every `ref_lat`/`ref_lon` and every `y_lat_future_*`/`y_lon_future_*` column |
| No duplicate `(sid, t_ref)` rows | `DataFrame.duplicated` |
| Window cadence is gap-free per storm | per-storm consecutive-`t_ref` diff must be exactly 6h — the observed-track reconstruction depends on this and refuses to proceed if it does not hold |
| Every declared model has benchmark rows | set-difference against the 6 expected model names |
| Reconstructed predicted positions stay in range | `pred_lat`/`pred_lon`, computed via `displace()`, re-validated post-hoc before insert |

### 5.2 Validation results (this run)

```
1732 windows, 88 storms -- validation passed
6 model versions from phase2_benchmark_results.json
Reconstructed 2084 observed points across 88 storms
```

### 5.3 Idempotency — proven, not asserted

Every write goes through `INSERT ... ON CONFLICT (<natural key>) DO UPDATE`, keyed on the same
`UNIQUE` constraints the migration created. **The script was run twice in immediate succession**
against the real database:

| Table | After run 1 | After run 2 |
|---|---|---|
| `model_versions` | 6 (ids 1–6) | 6 (**same ids** 1–6) |
| `storms` | 88 | 88 |
| `observations` | 2,084 | 2,084 |
| `predictions` | 41,568 | 41,568 |

Identical row counts and identical primary-key assignments across both runs — true no-op
re-ingestion, not merely "no error was thrown."

### 5.4 Cross-check against Phase 2's own numbers

The per-row `track_error_km` values this script computes (via the vendored `haversine_km`, §15)
were aggregated and compared to Phase 2's own stored benchmark metrics:

| Model | DB-computed mean @24h | Phase 2 benchmark @24h |
|---|---:|---:|
| `track_persistence` | 226.24 km | 226.2 km |
| `track_cliper` | 200.44 km | 200.4 km |
| `track_lightgbm` | 203.34 km | 203.3 km |

Exact match (to reported precision) — proves the ingestion pipeline introduces **zero numerical
drift** from Phase 2's validated results.

## 6. API Endpoints

Base path `/api/v1`, per `docs/API_ARCHITECTURE.md` §2. Resource name is `cyclones` (not `storms`)
in the URL, per that document's §3.1 — the Phase 3 task brief explicitly defers to the existing
architecture document's naming where the two differ; the underlying table and Python identifiers
are named `storms`, matching `docs/SYSTEM_ARCHITECTURE.md`'s schema.

| Method | Path | Purpose | Response |
|---|---|---|---|
| GET | `/health` | Liveness + DB connectivity | `{status, database}` |
| GET | `/api/v1/meta` | Project/API version, active models | `MetaResponse` |
| GET | `/api/v1/cyclones` | Paged storm list, filterable by `season`/`basin`/`split`/`q` | `Page[StormSummary]` |
| GET | `/api/v1/cyclones/{sid}` | Storm detail incl. bbox, `has_predictions` | `StormDetail` (404 if unknown) |
| GET | `/api/v1/cyclones/{sid}/observations` | Time-ordered observed track points | `list[ObservationOut]` (404 if unknown storm) |
| GET | `/api/v1/tracks/{sid}?t=` | **The map's payload** — one GeoJSON `FeatureCollection`, observed + predicted, for a forecast origin (defaults to the latest available) | `FeatureCollection` |
| GET | `/api/v1/prediction/{sid}?t=&task=&model=` | Scalar per-horizon forecast records for one origin | `list[PredictionOut]` (200 `[]` if the storm has no predictions at all; 404 if a specific filter matches none) |
| GET | `/api/v1/prediction/{sid}/series` | Every forecast issued across the storm's life | `list[PredictionOut]` |
| GET | `/api/v1/prediction/models/list?task=` | Model catalogue with full Phase 2 metrics | `list[ModelVersionOut]` |

**Not built (explicitly out of Phase 3 scope):** `/detection/*`, `/classification/*`,
`/analytics/*`, `/explain/*` — no model exists for the first two, and analytics/Gemini are later
phases.

### 6.1 Response shape rules, enforced

- Every route returns a typed Pydantic model — **zero routes return a bare `dict`.**
- Errors are RFC 7807 `problem+json` (`type`, `title`, `status`, `detail`, `instance`) — a global
  `HTTPException` handler in `app/main.py`, not ad hoc per-route error bodies.
- Every prediction-bearing response carries `model_name`/`model_version` and a literal
  `disclaimer` string — never a bare number.
- `data_kind` (`"observed"` \| `"model_prediction"`) appears on every observation and prediction
  payload, and on every GeoJSON feature's `properties.kind` — the observed/predicted distinction is
  structural, not a UI convention a client could get wrong.

## 9. Map Behaviour

`components/map/CycloneMap.tsx` renders the GeoJSON `FeatureCollection` the backend already
assembled — **no geodesic math, no reprojection, no client-side simplification**, per
`docs/SYSTEM_ARCHITECTURE.md` §6.1.

| Layer | Source `kind` | Visual treatment |
|---|---|---|
| Observed track | `observed_track` | **Solid** teal (`#22D3A7`) polyline |
| Observed points | `observed_point` | Small filled teal circles, popup shows OBSERVED wind/pressure |
| Predicted track | `predicted_track` | **Dashed** (`6 6`) line, one colour per model (amber/orange/purple family), never teal |
| Predicted points | `predicted_point` | Larger, semi-transparent circle markers matching their model's line colour; popup shows MODEL PREDICTION, model name+version, predicted wind, track error, and the disclaimer string |

**The mandatory distinction is enforced two ways, not one:** colour (teal vs. non-teal) AND line
style (solid vs. dashed) — so the map stays legible in greyscale, per
`docs/UI_UX_ARCHITECTURE.md` §8's accessibility rule. `tests/test_api_tracks.py::
test_observed_and_predicted_are_never_the_same_feature` additionally proves this at the data layer:
every `observed_*` feature's `data_kind` is exclusively `"observed"`; every `predicted_*` feature's
is exclusively `"model_prediction"` — a frontend bug cannot silently blur the two because the
underlying data never allows it.

No wind field, particle animation, or any rendering of a physical quantity the dataset does not
contain is present anywhere in the map — consistent with `docs/UI_UX_ARCHITECTURE.md` §3.1's
explicit rejection of a "physics/particle wind field" as data fabrication.

## 12. Known Limitations

- **No browser screenshot/E2E capture** (§11) — component tests and server-rendered HTML inspection
  are strong but not equivalent evidence.
- **`storms.name` and `storms.made_landfall` are always `null`.** The Phase 2 artifact
  (`phase2_test_predictions.parquet`) does not carry storm name or landfall flag — only `sid`,
  positions, and intensity. Backfilling these would require joining against raw IBTrACS, which was
  deliberately avoided to keep the ingestion script's only dependency the already-validated Phase 2
  artifact (see §15). Both fields are nullable in the schema for exactly this reason and the map/UI
  fall back to the SID when no name is present.
- **The forecast-origin time `t` is not yet mirrored into the URL** on `/predict/[sid]` — the page
  always shows the storm's latest available forecast origin. `docs/UI_UX_ARCHITECTURE.md` §5.4
  calls for `(sid, t)` in the URL for shareability; Phase 3 implements `sid` only. A `TimeScrubber`
  wiring `t` into the URL is deferred to a later frontend phase.
  \- **Only the North Atlantic 2010–2015 *test*-split storms are queryable** (88 storms) — this
  phase ingests `phase2_test_predictions.parquet` specifically, per the task's explicit instruction
  to use that artifact. Train/val storms exist in `ml/manifests/splits_v1.json` but have no
  predictions ingested (Phase 2 never generated predictions for them either — they were the
  baselines' *training* data).
- **No `GET /tracks/bulk`** (multi-storm overview map) — single-storm `/tracks/{sid}` only, per the
  task's minimal-endpoint list.
- **No response caching / `ETag`s** yet, despite `docs/API_ARCHITECTURE.md` §4 recommending them —
  a small vertical slice with ~90 storms does not yet need it; noted as a Phase 10 ("Integration &
  Hardening") item, not a Phase 3 gap that blocks anything.
- **Ports are non-default** (Postgres 5434, backend 8001, frontend 3001) because this workstation
  already runs other Docker Postgres/API/frontend stacks on the standard ports 5432/8000/3000 —
  documented in `infra/docker/docker-compose.yml` and both `.env.example` files, not a hidden
  surprise.

## 15. What Is Intentionally NOT Implemented

Per the Phase 3 task's explicit exclusion list — **none of the following were built, and none were
accidentally introduced**:

CNN · ResNet · GRU · LSTM · Transformer · HURSAT training · ADT training · Gemini / Gemini API calls
· authentication · WebSockets · Redis · Celery · GraphQL · Mapbox · deck.gl · GSAP · an advanced 3D
globe · production model serving · live weather ingestion · real-time or operational forecasting ·
storm warnings · rainfall or storm-surge prediction · damage estimation.

**Verified, not just declared:** `grep`-checked across `backend/` and `frontend/` for every term in
that list before finalising this phase; the only "GRU"/"LSTM"/etc. references anywhere in the
codebase are inside `docs/ML_ARCHITECTURE.md`'s own forward-looking design notes, never in code.

### 15.1 The one deliberate architectural exception, explained in full

`docs/SYSTEM_ARCHITECTURE.md` states three times that `backend/` must never import from `ml/`. The
ingestion script needs the Haversine great-circle formula and the wrap-safe displacement
reconstruction that Phase 2 already built, tested, and validated in
`ml/geostrom_ml/features/geo.py`. Two options were available: import `ml.geostrom_ml` into
`backend/scripts/ingest_phase2_predictions.py` (violating the "never imports from ml/" rule, even
though the script itself is not part of the served app), or re-implement the same ~30 lines of pure
math inside `backend/` (a narrow, bounded duplication of formulas, not of Phase 2's causal
feature-engineering or filtering logic).

**The second option was chosen** — `backend/app/services/geo.py` is a deliberate, documented
vendoring of `haversine_km`/`displace`/`wrap_lon_diff` from `ml/geostrom_ml/features/geo.py`, with
a docstring explaining exactly why. This keeps `backend/`'s dependency graph free of pandas/ML
concerns entirely (confirmed: `backend/requirements.txt` needs `pandas`/`pyarrow` only for the
*ingestion script* to read the Parquet file, not for the served API), honours the stronger
architectural rule, and is proven — not just claimed — to introduce zero numerical drift by the
exact-match cross-check in §5.4.
