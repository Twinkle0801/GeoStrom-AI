## 5. Scene Semantics (evidence, not invention)

Per the task's explicit instruction not to invent scientific definitions, every semantic
claim below cites a specific, pre-existing project source.

**Source 1** — `docs/PROJECT_REQUIREMENTS.md` (Phase 0, "Tier B"): *"Eye, Embedded Centre,
Central Dense Overcast, Irregular CDO, Curved Band, Shear, Uniform"* — named explicitly as
the ADT/Dvorak scene-type label set, later promoted to primary classification target by
`docs/DATA_STRATEGY.md` decision #14 once Phase 1 confirmed the field exists.

**Source 2** — `ml/scripts/verify_adt.py` (Phase 1, verified against real ADT files):
```python
EYE_SCENE   = {0: "Eye", 1: "Pinhole Eye", 2: "Large Eye", 3: "No Eye"}
CLOUD_SCENE = {0: "CDO", 1: "Embedded Center", 2: "Irregular CDO",
               3: "Curved Band", 4: "Shear"}
```
with the `Scene` field documented (in the same script's own report metadata) as "a
combination of EyeScene and CloudScene integer codes".

| Label | Evidence | Interpretation | Category (A/B/C/D, see Task 3) |
|---|---|---|---|
| CDO | Both sources | Central Dense Overcast — a genuine, common Dvorak pattern | **A** valid, well-represented |
| CurvedBand | Both sources | Curved Band — spiral banding, precursor/organizing structure | **A** valid, best-represented (12/12 storms) |
| Shear | Both sources | Shear — vortex exposed/displaced from convection | **A** valid, well-represented |
| Eye | Both sources | A clear eye is visible | **A** valid, but storm-thin (5 storms) |
| EmbCenter | Both sources | Center inferred through convection, no clear eye | **B** transitional — sits between CDO and Eye; too storm/sample-thin to stand alone (§7) |
| LargeEye | Source 2 only (EYE_SCENE code 2) | A **size variant** of Eye, not a distinct pattern | **D** requires grouping (with Eye) |
| IrrCDO | Source 2 only (CLOUD_SCENE code 2) | A **shape variant** of CDO, not a distinct pattern | **D** requires grouping (with CDO) |
| Land | **Neither source** | See below | **C** unsuitable as a storm-pattern class |

**`Land`**: absent from both the Phase 0 Tier B list and the EYE_SCENE/CLOUD_SCENE code
tables. `ml/scripts/verify_adt.py` itself treats it specially — counted separately
(`land_records`, `pct_land_records`) and explicitly **excluded** from what it calls the
"real" scene distribution (`scene_distribution_excluding_land`). This is documented
codebase evidence, not a Phase 5 guess, that `Land` functions as a geographic/QC override
(the storm centre sits over land, where Dvorak pattern analysis is not meaningful) rather
than a genuine storm-structure category.

**Confidence statement, per the task's explicit instruction**: the CDO/CurvedBand/Shear/Eye
interpretations are HIGH confidence (named in two independent pre-existing sources). The
LargeEye/IrrCDO-as-variants interpretation is HIGH confidence (directly from the verified
EYE_SCENE/CLOUD_SCENE code tables). The `Land`-as-geographic-override interpretation is
**evidence-based but not a directly-quoted NCEI definition** — stated with that caveat
rather than presented as settled fact. `EmbCenter`'s exact structural meaning beyond "center
inferred, no clear eye" (e.g. exactly how the ADT algorithm distinguishes it from a hazy
CDO) is **not resolved** by any source in this project — marked unresolved rather than
guessed, per the task's explicit instruction.

**Uniform**: Phase 0's Tier B list included "Uniform" as a possible scene value; it never
occurs in the verified EYE_SCENE/CLOUD_SCENE tables or the real 627-sample dataset. Noted
as a superseded planning-stage guess, not a contradiction.

## 6. Candidate MVP Taxonomies

### Option A — 8-class (all real Scene labels, unchanged)

| | |
|---|---|
| Classes | CDO, CurvedBand, Land, Shear, Eye, EmbCenter, LargeEye, IrrCDO |
| Samples | 627 |
| Storms | 12 |
| Train/val/test | 404 / 128 / 95 samples (all 7/2/3 storms) |
| Advantages | No information discarded; matches the "true" ADT output most literally |
| Disadvantages | 3 of 8 classes have <6 storms; `LargeEye` (3 storms) and `IrrCDO` alone in val=0 cannot be evaluated reliably at all; `Land` is not a storm-pattern class (§5) and would teach the classifier to recognise "not over water" rather than storm structure |
| Scientific interpretation | Technically the ground truth, but statistically indefensible at this sample size — a per-class metric for `LargeEye` is really a statement about 2-3 storms |
| Modeling difficulty | High: severe 16x imbalance (CDO 177 vs IrrCDO 11), multiple classes with near-zero test/val support |
| Risk of misleading results | **High** — a model could achieve a seemingly reasonable macro-average while its `LargeEye`/`IrrCDO`/`EmbCenter` numbers are noise from 1-3 storms, not a real capability |

### Option B — Reduced, evidence-grounded taxonomy (`scene_taxonomy_v1`) — **RECOMMENDED**

| | |
|---|---|
| Classes | CDO (+IrrCDO), CurvedBand, Eye (+LargeEye), Shear — `Land` and `EmbCenter` excluded, not merged |
| Samples | 521 included / 627 total (83.1%) |
| Storms | 12 (every storm retains at least one included sample) |
| Train/val/test | 353 (7 storms) / 88 (2 storms) / 80 (3 storms) |
| Advantages | Every merge groups sub-codes the ADT algorithm's OWN code tables already recognise as the same family (§5) — not an invented axis. All 4 final classes have ≥5 storms; 3 of 4 have ≥10 storms |
| Disadvantages | `Eye` (merged) still has **zero test-split samples** — merging doesn't fix a class the frozen test storms simply never exhibit (§3/§7); only 521/627 samples usable |
| Scientific interpretation | A defensible sub-type consolidation of genuine Dvorak scene types, explicitly NOT a new ground truth (see §5 circularity discussion) |
| Modeling difficulty | Moderate: 4 classes, 2.3x sample imbalance (CDO 188 vs Shear 83) — addressed via class weighting (§8), not resampling |
| Risk of misleading results | Present but bounded and explicitly reported: the `Eye`-class zero-test-support limitation is documented, not hidden (§7, §9) |

### Option C — Binary/coarse taxonomy ("organized" vs "sheared") — considered, NOT recommended

| | |
|---|---|
| Classes | e.g. `Organized` (CDO+CurvedBand+Eye+EmbCenter+IrrCDO+LargeEye) vs `Sheared` (Shear); `Land` still excluded |
| Samples | ~455 "Organized" / 83 "Sheared" of 627 (illustrative split; not built into a pipeline this phase) |
| Storms | Shear present in 10/12 storms; "Organized" in effectively all 12 |
| Advantages | Would trivially solve the storm/sample-thinness problem (only 2 classes, both well-represented) |
| Disadvantages | **The organized/sheared boundary is NOT directly named in either semantic source (§5)** — it requires inventing a new axis (which of the 6 sub-types count as "organized"?) that the ADT code tables do not themselves draw. `EmbCenter` and `CDO` are structurally quite different (clear-vs-inferred center) yet would be forced into the same bucket |
| Scientific interpretation | This is precisely the risk the task's `Developing/Organized/Mature/Weakening` warning describes: a plausible-sounding grouping not grounded in the source taxonomy. `docs/PROJECT_REQUIREMENTS.md`'s "Tier C" caveat — "engineered, not ground truth... risk of circularity" — applies directly |
| Modeling difficulty | Low (binary, well-balanced) — but low difficulty here is a red flag, not a benefit: it would come from discarding real structural information, not from the classifier learning something meaningful |
| Risk of misleading results | **High** — an apparently strong binary accuracy could mislead a reader into thinking GeoStrom AI performs genuine Dvorak-family classification, when it would really be a shear-detector with an invented "everything else" bucket |

### Selection

**Option B (`scene_taxonomy_v1`) is selected.** It is the only option whose class
boundaries are directly traceable to the ADT algorithm's own internal code tables (no
invented axis, unlike Option C) while still being statistically usable (unlike Option A).
Its remaining limitation — zero `Eye` samples in the frozen test split — is a property of
the small 12-storm dataset, not fixable by any taxonomy choice, and is reported explicitly
throughout this document and in the baseline results rather than concealed.

## 7. Excluded / Merged Labels — Exact Reasons

| Original label | Disposition | `exclusion_reason` | Evidence |
|---|---|---|---|
| IrrCDO | merged into `CDO` | — | CLOUD_SCENE code 2, a documented shape variant of CDO (code 0); alone: 11 samples/6 storms, 0 in val |
| LargeEye | merged into `Eye` | — | EYE_SCENE code 2, a documented size variant of Eye (code 0); alone: 14 samples/3 storms (below the 4-storm threshold), 0 in test |
| `EmbCenter` | **excluded** | `insufficient_label_support` | 17 samples / 5 storms overall, but only **1 sample in the entire test split** — no per-class test metric could be meaningful. Not merged into CDO or Eye because CLOUD_SCENE lists it as its own co-equal code (1), not a documented variant of either (§5) |
| `Land` | **excluded** | `land_contaminated` | Absent from both semantic sources; `verify_adt.py`'s own precedent of excluding it from the "real" scene distribution (§5) |

Both exclusion reasons are machine-readable constants in
`ml/geostrom_ml/classification/taxonomy.py` (`EXCLUSION_INSUFFICIENT_SUPPORT`,
`EXCLUSION_LAND_CONTAMINATED`), plus `EXCLUSION_UNRESOLVED_MAPPING` for any future label the
taxonomy has not seen (never silently dropped — see `apply_taxonomy`'s NaN/unknown-label
handling).

## 8. Class Imbalance Analysis

`ml/geostrom_ml/classification/imbalance.py`. Training-split class counts (final taxonomy):
CDO 144, CurvedBand 101, Eye 58, Shear 50 — a 2.9x imbalance ratio (down from 16x in the raw
8-class data, mostly via exclusion rather than merging).

**Strategy applied this phase**: `class_weight='balanced'` for logistic regression
(scikit-learn's standard inverse-frequency formula, computed from the TRAINING split
`compute_class_weights()` reproduces explicitly for transparency), and an equivalent
`class_weight` dict passed to LightGBM. Training-split weights:
`{CDO: 0.61, CurvedBand: 0.87, Eye: 1.52, Shear: 1.77}`.

**Explicitly NOT used**, per the task's prohibition: naive random oversampling (could
duplicate a single storm's frames — with only 7 training storms, this risks a class
becoming "one storm, upsampled" rather than genuinely represented), SMOTE on pixels, or any
synthetic image generation.

**Phase 6 plan** (specified, not trained, in `imbalance.py::PHASE_6_IMBALANCE_STRATEGY`):
weighted cross-entropy with the same training-split-only weights, optional label smoothing,
macro-F1 as the model-selection metric, and mandatory per-class recall + confusion matrix
reporting every evaluation. Every technique operates on the loss function, never on the
data, so none of them can move a storm's samples across the frozen split boundary.

## 10. Baseline Results

Three non-deep-learning models, all trained on the TRAIN split only, evaluated on
train/val/test. Features (`ml/geostrom_ml/classification/features.py`, 19 deterministic
statistics per frame: global mean/std/min/max/percentiles, valid-pixel fraction,
center/ring/outer-region means and their differences, four quadrant means and their
spatial std) are extracted directly from the canonical Zarr `irwin_k`/`valid_mask` arrays —
**no IBTrACS field, no future information, no field beyond the two pixel arrays is even
passed to the feature function** (enforced structurally: `extract_features(kelvin,
valid_mask)` takes exactly those two arguments — see
`test_classification_leakage.py::TestVector4NoFutureIbtracsAsFeatures`).

| Model | Train macro-F1 | Val macro-F1 | **Test macro-F1** | Test accuracy |
|---|---:|---:|---:|---:|
| Majority-class (predicts `CDO`) | 0.145 | 0.124 | **0.079** | 0.188 |
| Logistic Regression (balanced) | 0.769 | 0.494 | **0.559** | 0.763 |
| LightGBM (class-weighted) | 1.000* | 0.509 | **0.541** | 0.713 |

\* LightGBM reaches 100% train accuracy/F1 — visible overfitting on 353 training samples
despite depth/leaf constraints, reported honestly rather than hidden. Its test performance
is close to but slightly below logistic regression's, which generalises more smoothly.

**Best model by the primary metric (test macro-F1): Logistic Regression (0.559)**,
comfortably beating the majority-class floor (0.079) by ~7x.

Because `Eye` has zero test-split support (§3), `macro_f1` above is computed with `Eye`
included at zero precision/recall/support (scikit-learn `zero_division=0`) — a
**conservative** number. A second figure, `macro_f1_over_present_classes_only` (computed
over just `CDO`, `CurvedBand`, `Shear` — the classes the test split can actually evaluate),
is also reported per the honesty requirement: **0.746** for logistic regression, **0.721**
for LightGBM, **0.105** for majority-class. Both numbers are in every result record
(`ml/reports/phase5_baseline_results.json`); neither is presented as the sole truth.

Full per-class precision/recall/F1/support, and results for the train/val splits too, are
in `ml/reports/phase5_baseline_results.json`.

## 12. Leakage Validation

`ml/tests/test_classification_leakage.py` — 10 vectors, each with a passing test on clean
data AND, where meaningful, an adversarial test that deliberately introduces the bad
condition and proves a real validator (`ml/geostrom_ml/classification/leakage.py`) catches
it (not merely a pytest assertion in isolation):

| # | Vector | Adversarial proof |
|---|---|---|
| 1-2 | Storm cannot appear in >1 split | A storm forced into train+val is caught by `find_storm_split_violations` / `assert_no_storm_split_leakage` raises |
| 3 | Labels come from allowed metadata only | Mutating every OTHER column leaves `final_class` unchanged; `apply_taxonomy`'s signature takes only `scene_label` |
| 4 | No future IBTrACS as features | `extract_features`'s signature is exactly `(kelvin, valid_mask)` — structurally cannot read `usa_wind`, `max_wind`, etc. |
| 5 | Excluded samples can't enter training | An excluded row planted in a "clean" selection is caught by `find_excluded_rows_in_selection` / `assert_no_excluded_rows` raises. Also wired into `run_classification_baseline.py` itself as defense-in-depth |
| 6 | Original Scene unchanged | Real-data test: every row's `original_scene` in the committed classification index matches Phase 4's `scene_label` exactly |
| 7 | Deterministic mapping | Repeated calls to `apply_taxonomy`/`build_classification_index` agree |
| 8 | Reproducible dataset creation | Two independent `build_classification_index` calls produce a byte-identical DataFrame (`pd.testing.assert_frame_equal`) |
| 9 | Test set never used for taxonomy selection | `SCENE_TAXONOMY_V1` is a static module-level dict; `apply_taxonomy` takes no split/data argument |
| 10 | Class weights from training split only | `compute_class_weights`'s signature takes one Series; an adversarial call with val+test mixed in produces visibly different weights, proving the function is sensitive to (and therefore must be given) the correct input |

Real-data confirmations (skip cleanly if artifacts absent): the committed classification
index has zero storm/split violations; `splits_v1.json` itself remains storm-disjoint
across train/val/test (re-verified, not just assumed, since Phase 5 never modifies it).

## 14. Limitations

- **`Eye` has zero test-split samples.** An irreducible consequence of which 3 storms the
  frozen Phase 2 split assigned to test — not fixable without creating a new split (not
  permitted this phase) or downloading more archive (not permitted this phase).
- **Only 12 storms total** (7/2/3 by split) underlie every number in this document. Even
  the "well-represented" classes (CurvedBand, CDO, Shear: 10-12 storms) are a small
  population; results should be read as a genuine but early signal, not a mature benchmark.
- **`val` has only 2 storms** — its own metrics (e.g. `Shear` val support = 2 samples from 1
  storm) are correspondingly noisy; reported for completeness, not relied upon for any
  selection decision (none was made — see §10's no-hyperparameter-search note).
- **LightGBM overfits** the 353-sample training set (100% train accuracy) despite
  depth/leaf constraints — a real property of tree ensembles at this scale, reported rather
  than tuned away.
- **`EmbCenter`'s exact structural definition is unresolved** (§5) — excluded on sample-
  support grounds, not because its meaning is understood and rejected.
- **Full 531-storm archive has NOT been processed.** This document's entire evidence base is
  the same 627-sample Phase 4 dataset that has been real and unchanged since Phase 4; no
  claim in this document should be read as describing the full archive.

## 15. Phase 6 Readiness Assessment

Phase 6 (CNN classification training) **can begin** using: the frozen taxonomy
(`scene_taxonomy_v1`), the classification dataset index, the documented imbalance strategy,
and the non-deep-learning baseline as its minimum bar to beat (test macro-F1 > 0.559,
logistic regression). Before or during Phase 6, it would be valuable (not blocking) to
enlarge the dataset via the existing idempotent Phase 4 pipeline (`download_hursat_sample.py`
+ `build_satellite_dataset.py`, no code changes needed) specifically targeting more `Eye`-
and `EmbCenter`-bearing storms, since those are this phase's thinnest classes. Phase 6 must
preserve every constraint validated here: frozen storm-level split, training-split-only
class weighting, macro-F1 as the primary metric, and full per-class + confusion-matrix
reporting every evaluation.
